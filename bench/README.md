# bench

压测套件。回答一个问题：**这个运行时在并发下，时间花在哪。**

跑出来的报告见 [`RESULTS.md`](RESULTS.md)。

```bash
pip install -e .
python -m bench.run                                # quick 预设，几秒
python -m bench.run --full --out bench/RESULTS.md  # 出报告，约 1 分钟
```

## 核心约定：模型调用全部 stub

这不是实现细节，是这套压测成不成立的前提。

真实模型调用要走网络，耗时由上游决定，比运行时自身的开销高一到两个数量级。
拿真模型压测，量出来的是**别人的网络延迟**，跟自己写的代码没关系——
一次「P95 2.3 秒」的结果，无法回答「是不是我这段代码慢」。

所以 `stub_provider.py` 把模型延迟变成**可控参数**：固定成某个值，
端到端延迟减去它，剩下的才是这个仓库该为之负责的部分。
报告里每一处都标了扣减口径。

副产品是结果可复现，且不花钱、不联网——CI 里也能跑。

## 三个场景各自隔离一层成本

混在一起测就只能得到一个总数，而总数无法定位问题。

| 场景 | 隔离的是什么 | 为什么单独测 |
|:--|:--|:--|
| `1. 事件日志写入` | 唯一的同步 I/O：每次 append 都 `fsync` | 最可能成为瓶颈，也最容易改错方向 |
| `1b. 写入争用` | 每会话那把 `asyncio.Lock` | 判断锁本身是不是瓶颈，还是它背后的盘 |
| `2. 读取与重放` | `store.read()` 与 `project()` 拆开计时 | 验证 ADR 0001 的「先不做快照」在什么规模上还成立 |
| `3. 端到端轮次` | 全链路，并发多会话 | 唯一能回答「并发下什么样」的场景 |

场景 2 生成数据时**直接写文件、绕开逐条 append**——测的是读，不是写，
否则造数据的时间会比测量本身还长。

## 口径

- 报 **p50 / p95 / p99**，不报平均值。平均值会被长尾藏住，而长尾正是并发场景的痛点。
- 同步函数计时取多次**最小值**，异步耗时逐次记录。最小值最接近代码本身的成本。
- 每个场景跑之前先预热，让 import、页缓存、首次建文件都发生在计时窗口之外。
- 报告里出现的每个数字都对应表里的一行；结论区的比例由**原始数值**算出
  （`ScenarioResult.metrics`），不由格式化过的字符串反推——改显示格式不会让算术悄悄错掉。

## 报告怎么读

`report.py` 里的结论区只写压测**直接支撑得了**的话，推不出来的进「已知限制」。
另外两处刻意设计：

- **归因要标口径**。拿 A 场景的 p50 去乘 B 场景的次数，是常见的错误归因——
  两个场景并发度不同，fsync 的排队延迟也就不同。所以那种比较只作量级校验，
  报告里明写了「不能当精确归因」。
- **算不出来的结论不如不算**。某次实现在结论区印出过「fsync 占 120%」——
  超出 100% 的归因必然是方法有问题，不是数据有问题。现在这类比例改成
  两边并排给出、由读者判断量级。

## 已知限制

- 只测单进程单事件循环。多进程/多实例部署下的事件日志没有覆盖，
  而 fsync 的并发表现恰恰是最吃环境的一项。
- `fsync` 的绝对值强依赖平台与磁盘。当前数字来自 Windows + NTFS，
  明显偏悲观；换平台会变，但「fsync 占大头」这个结论不会。
- 工具用内置的 `echo`，不做真实 I/O。真实工具慢下来会另成一个瓶颈。
- 模型延迟是常量，没有模拟网络抖动、重试、上游限流。
