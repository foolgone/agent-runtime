# ADR 0001：会话持久化用 append-only 事件日志

- 状态：已采纳
- 日期：2026-10-08

## 背景

Agent 的一轮对话不是一个请求，而是一串：用户输入 → 模型输出 → 工具调用 → 工具结果 →
模型再输出……中间任何一步都可能失败，进程也可能在任何一步被杀掉。

需要回答的问题是：**进程重启之后，怎么知道上一轮跑到哪了？**

具体到必须有答案的场景：

- 工具调用已经发出去了，但结果没写回来。这个工具有没有执行？执行了几次？
- 用户重试同一个请求。会不会产生第二份副作用？
- 一条会话跑到第 5 次工具往返时服务重启，重放时能不能接着往下走？

## 备选方案

### 方案 A：可写状态表

一张 `sessions` 表存 `{messages: json, status: str, updated_at: ...}`，每次状态变化 `UPDATE` 一次。

- 优点：读快，实现直白，任何人一眼看懂。
- 缺点：**丢失中间状态**。`UPDATE` 只保留最后一个版本，崩在「工具已调用、结果未写回」的那一刻，
  表里就是上一次 `UPDATE` 的内容——那次调用在数据里完全不存在。要恢复就得靠猜，
  或者额外引入检查点机制。而 `messages` 字段每轮全量重写，写放大也随对话线性增长。

### 方案 B：append-only 事件日志（本方案）

一条会话一个追加文件，每次状态变化追加一条事件，当前状态由重放推出。

- 优点：崩溃点天然可见（有 `tool/call` 没 `tool/result` 就是它）；追加是顺序写，
  没有读-改-写竞争；日志本身可读、可 grep、可重放，排查不需要额外工具。
- 缺点：重放成本随事件数线性增长；查询当前状态要先读全量。

### 方案 C：事件日志 + 定期快照

在 B 的基础上定期写检查点，重放从最近的检查点开始。

- 优点：兼顾写入顺序性和读取代价。
- 缺点：多一套快照一致性逻辑（快照和日志尾巴的边界怎么对齐、快照写到一半崩了怎么办），
  而这些正是 B 想避开的复杂度。

## 决策

采纳 **方案 B**。理由：

1. **崩溃恢复不需要额外机制。** 日志本身就是恢复所需的最小信息。方案 A 的恢复要额外设计，
   方案 C 要额外设计两遍（快照 + 边界）。
2. **「已受理、结果未知」是一个必须能被表达的状态。** 这个状态在方案 A 里没有容身之处——
   它是一条写入被中断的记录，而 `UPDATE` 的语义是覆盖。日志里它就是一条没有配对结果的事件，
   天然存在。
3. **重试的决定权留给调用方。** 日志让未收尾的调用**可见**，但运行时不去猜要不要重试。
   重试写操作可能产生第二份副作用，这个判断需要业务语义，不该由存储层替用户拿主意。

方案 C 不是被否决，是被推迟：等重放成为实测瓶颈再做，那时快照的收益才可衡量。
当前实现里一轮对话的事件数是几十条量级，重放代价可以忽略。

## 影响

**变得容易的：**

- 崩溃恢复、审计、调试共用同一份数据。
- 「正常执行」和「恢复后继续」走同一条代码路径——都是「读日志 → 重放 → 继续」。
  恢复路径不会因为没人测而过期。
- 加新事件类型只是加一个字符串常量，不用改表结构。

**变得困难的：**

- 重放是 O(n)。会话很长时有成本，需要快照才能压下去。
- 事件 schema 的演进要向前兼容：旧版本写的事件，新版本代码也得能读。
  处理方式是重放时对未知字段宽容、对未知事件类型记为异常而不是抛错。
- 「当前状态」没有唯一真相行可查，必须重放或者读缓存。

**由此确立的两条实现约束：**

1. **先记账，后执行。** 工具调用在真正执行之前就先写 `tool/call`。
   反过来（先执行再记账）会让崩溃点落在记录之外，整个方案的核心收益就没了。
2. **写完要 fsync。** 只 flush 到用户态缓冲，进程被 kill 时最后几行会丢——
   而丢掉的恰好可能是最关键的「工具已经调用了」那条。
